# Security SOTA Report — 2026-11-11

**TL;DR**: In 2026, coding-agent tool-allowlist security keeps failing the same way across the industry: Cursor shipped CVE-2026-22708 (shell builtins bypassing its Auto-Run allowlist) and has four independently documented denylist bypasses; Aider disables all confirmation prompts repo-wide via a committed config flag; a 2026 arXiv survey (2606.15549) finds terminal-agent command denylists broadly fragile — explicitly including Claude Code's own built-in denylist, the host Ruflo itself runs on. Tonight's deep review found Ruflo has its own instance of this exact class, in the one place built specifically to catch it: `settings-risk-scanner.ts`'s `scanAllowRuleForRisk()` heuristically flags `permissions.allow` rules that pre-approve a shell/interpreter word (`bash`, `sh`, `python`, `ruby`, `perl`, …) with no per-call confirmation — but `node`, `deno`, `bun`, and `php` are absent from that word list, despite being GTFOBins-documented shell-breakout interpreters in exactly the same tier as the four already covered. This repo's own committed `.claude/settings.json` carries a live, fully-unscoped `"Bash(node:*)"` allow-rule today that the scanner silently passes as clean. Fixed tonight by extending the word list and its test coverage; a DNS-rebind SSRF gap flagged as a deferred finding on 2026-10-30 was also found, on inspection, to already be closed (`http-fetch-pinned.ts`'s `pinnedLookup`, ADR-164 §5.1.8) — recorded here as a correction, not re-implemented.

**Why this isn't "None across the board"**: no competitor implements the same static heuristic-scanner mechanism Ruflo does (see Competitor Comparison) — the field splits between pure list-membership (Cursor/Windsurf, both with documented bypasses) and OS-level sandboxing (OpenAI Codex CLI, architecturally different). That absence is itself the finding: Ruflo's approach is more sophisticated than most reviewed competitors', which makes its own gap worth closing rather than dismissing as "everyone has this."

## Ruflo Current Capability

`v3/@claude-flow/cli/src/init/settings-risk-scanner.ts` is Ruflo's advisory-only scanner, run by `ruflo init --upgrade` against a target project's pre-existing `.claude/settings.json` (built 2026-08-16 against the CVE-2025-59536 hook-injection class). `scanAllowRuleForRisk()` flags a bare wildcard (`Bash(*)`) and any rule pre-approving one of `RISKY_PREAPPROVE_WORDS = [...DANGEROUS_COMMAND_WORDS, ...SHELL_EXEC_WORDS, ...DOWNLOADER_WORDS]` = `rm/rmdir/del/format/mkfs/dd/chmod/chown/kill/killall/pkill/reboot/shutdown/poweroff/halt/sudo/eval/bash/sh/zsh/python/python3/perl/ruby/curl/wget`. `node`/`deno`/`bun`/`php` are absent. The existing test file (`__tests__/settings-risk-scanner.test.ts`) pins `['Bash(node:*)']` in its "does not flag" list — checked, this is not a documented deliberate tradeoff (no comment, no commit message explaining it; repo history for this file is one squashed commit, `56fe4dc6`, uninformative). Confirmed the gap is live: `ruflo init`'s own default `generateSettings()` (`settings-generator.ts:32-42`) emits only `['Bash(npx @claude-flow*)', 'Bash(npx claude-flow*)', 'mcp__claude-flow__*']` — it never generates a node-related allow rule itself, so this repo's own committed `.claude/settings.json` lines 14/29 (`"Bash(node .claude/*)"`, `"Bash(node:*)"`) were hand-added, not scanner-exempted by design. The broader, fully-unscoped `"Bash(node:*)"` rule pre-approves *any* future `node` invocation — including a one-liner a prompt-injected file or compromised dependency could induce an agent to run — with zero per-call confirmation, and the scanner that exists specifically to flag exactly this shape says nothing.

Also verified tonight (correction, not a new fix): the 2026-10-30 ledger note's deferred finding — "`http_fetch`'s allowlist never resolves hostnames before the private/public decision" (DNS-rebind SSRF) — is **already closed**. `http-fetch-pinned.ts` (ADR-164 §5.1.8) implements `pinnedLookup`: the socket's own DNS lookup *is* the check, and the connection is pinned to the addresses that lookup returned, closing the TTL-0 rebind window the 10-30 note was concerned about. No action needed; flagged here so a future night doesn't re-open it.

## Hypothesis

> Given `settings-risk-scanner.ts`'s `scanAllowRuleForRisk()`, which currently returns a finding for `permissions.allow` rules pre-approving `bash/sh/zsh/python/python3/perl/ruby/curl/wget` (plus dangerous command words) with no per-call confirmation but returns no finding for an equivalent pre-approval of `node`, `deno`, `bun`, or `php` — GTFOBins-documented shell-breakout interpreters in the same risk tier as the four already covered — when `node`/`deno`/`bun`/`php` are added to `RISKY_PREAPPROVE_WORDS`, then `scanAllowRuleForRisk('Bash(node:*)')` and the equivalent `deno`/`bun`/`php` forms should return a non-empty finding, while every currently-passing test case (including `Bash(npm test)`, `Bash(git:*)`, `Read(*)`, and `scanCommandStringForRisk`'s separate, unrelated `node -e` hook-command exemption) remains unchanged, subject to: zero change to `scanCommandStringForRisk` (a different function governing fixed hook-command strings, already correctly scoped), zero new false positive against `ruflo init`'s own default-generated settings.json (which contains no node/deno/bun/php allow-rule today), deterministic $0 Vitest evaluation. Frozen before evaluation; not modified after.

**Independent adversarial critique**: a fresh-context critic agent (no access to this session's reasoning) independently re-read the diff, re-ran stash-isolation itself (confirmed byte-identical 5/54-fail-baseline → 54/54-pass-candidate), diffed `tsc --noEmit` output baseline-vs-candidate line-for-line (zero difference), and worked through the full reward-hack checklist, independently verifying the motivating fact (this repo's own `.claude/settings.json:29` really does carry `Bash(node:*)`) rather than trusting the write-up. Returned **CONFIRMED** + **PASS** for shippability. The critic additionally discovered, on its own initiative while running tests broader than the two files this session pointed it at, that a dedicated CJS/TS parity-guard test (`__tests__/session-start-hook-settings-risk-scan.test.ts`) checks `settings-risk-scanner.ts`'s TS implementation against a hand-ported CJS mirror in `hook-handler.cjs` (used by the `session-restore` hook that runs on every real session boot, per the 2026-10-11 ledger fix) — and that this session's original fix, by only touching the TS side, would have silently left that mirror out of sync on the exact interpreter-word cases this fix cares about. The critic ported the identical `INTERPRETER_WORDS` change into both copies of `hook-handler.cjs` (root and `v3/@claude-flow/cli/.claude/helpers/`, which must stay byte-identical) and extended the parity test's sample set to include `node`/`deno`/`bun`/`php` so this class of drift would be caught automatically going forward. Verified independently by this session: 71/71 pass across the three affected test files with the critic's fix applied.

Three non-blocking caveats disclosed by the critic, two closed same-session, one left as documented design rationale:
1. The regex terminator class (`(:| |\))`, not a generic `\b`) correctly avoids false-positiving on a prefix collision (`Bash(nodemon:*)`, `Bash(phpunit:*)`, `Bash(bunx:*)`, `Bash(denoland:*)` all correctly pass clean) — verified by hand but untested. **Closed same session**: added a dedicated regression-test block for exactly these four cases (75/75 pass after).
2. Separating `INTERPRETER_WORDS` from `SHELL_EXEC_WORDS` is design-justified (keeps `scanCommandStringForRisk`'s hook-command exemption for legitimate `node <script>` invocations untouched) but isn't proven load-bearing by any test that would currently regress if the two arrays were merged (no existing "does not flag" command-string sample combines `node` with a downloader word). Left as documented rationale in-source; not a correctness bug, just an untested design boundary.
3. The `hook-handler.cjs` changes weren't part of this session's original change summary to the critic — confirmed independently to be a necessary, correctly-mirrored consequence (CJS/TS parity), not drift or corruption from a concurrent session (the CLAUDE.md-documented risk this repo explicitly warns about).
