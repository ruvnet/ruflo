# Intelligence SOTA Report — 2026-09-27

TL;DR: Last night (2026-09-22, #3395) fixed an inverted EMA direction in `EWCConsolidator`'s Fisher-matrix update. That fix's own gist recommended, as future work, exploring whether `fisherDecayRate` (default 0.01) is actually the best value now that the direction is correct. Tonight makes that exploration *possible* — `fisherDecayRate` gets a `CLAUDE_FLOW_FISHER_DECAY` env override, mirroring the exact `envPriorDecay()`/`envMaxUncertainty()` pattern from `model-router.ts` — but does **not** claim to have found a better value: no real downstream task in this repo yet measures whether one decay rate protects patterns better than another, and this session declined to fabricate a synthetic fitness function just to produce a Darwin result. Also verified (SCAN, not selected): a real, tested Ed25519 plugin-integrity verifier sits completely unwired from the live `plugins install` path (capabilities), and two independent memory-surface inefficiencies survive PR #3266/product-quantization's fixes (`mmrRerank()`'s cosine recompute; HNSW's binary/scalar quantization dispatch).

## Darwin Results

**Skipped — for a new reason tonight, not the usual one.** Every prior night skipped Darwin because the candidate was a binary correctness fix with no continuous parameter (#3110/#3160/#3184/#3221/#3243/#3266/#3302/#3330/#3378/#3385/#3395). Tonight is different: `fisherDecayRate` genuinely is now a real, correctly-directioned, bounded `(0,1]` scalar — Darwin's real interface (`npx ruvector harness darwin <config> --execute`, confirmed available) could in principle sweep it. It was not invoked because doing so honestly requires a **fitness function tied to a real downstream outcome** (does a given decay value actually protect useful patterns better?), and no such signal exists in this repo yet — the existing/new tests validate EMA *direction* and *env-wiring correctness* at fixed decay values, not a quality tradeoff across values. Building a synthetic proxy (e.g., an invented "important vs. noise" discrimination score) purely to have something to feed Darwin would produce a number shaped like evidence without being it, which this session declined to do (per this Dream Cycle's own invariant against fabricated benchmarks). Recommended: a future night should build a real fitness signal first — e.g., replay a real trajectory history through `intelligence.ts`'s actual `distillLearning()` path and measure downstream pattern-reuse/success-rate under different decay values — then run Darwin against *that*, not a synthetic stand-in.

## Scan Findings: capabilities

`v3/@claude-flow/cli/src/commands/plugins.ts`'s `installCommand` (~209-321) declares a `--verify` flag (default `true`, "Verify checksum") that is read into a local `const verify` and then **never referenced again** — dead. `v3/@claude-flow/cli/src/plugins/manager.ts`'s `installFromNpm()`/`installFromLocal()` (~149-281) have no signature/checksum/`trustLevel`/`permissions` parameter at all; `trustLevel`/`permissions` are read from the registry entry only to *print* them in the post-install summary box. `enable()` logs a `[SECURITY]` console warning ("Plugin loaded without sandboxing... full process access") but that's the only control present besides an npm-injection guard on the package name. This is live, shipped CLI surface (registered in `commands/index.ts`), not dead code — no MCP tool wraps it, so the only path is direct CLI use, but that path runs `npm install` against an attacker-influenced package name with zero policy gate.

The sharper finding: a **real, tested** Ed25519 verifier already exists for exactly this purpose — `v3/@claude-flow/security/src/plugins/integrity-verifier.ts`'s `PluginIntegrityVerifier` (canonical-JSON manifest hashing, trust-anchor allowlist, its own test suite), built for ADR-145 ("P1", **Status: Proposed**, not Accepted/Implemented) and referenced again by ADR-337 (also Proposed). Its own doc comment states the threat model explicitly: the plugin install path fetches manifests from IPFS with **no signature verification and no intent analysis**. `v3/@claude-flow/cli/src/plugins/trust/trust-anchors.json` exists but holds only a placeholder all-zero key awaiting a real signing-key ceremony. Nothing in `plugins.ts`/`manager.ts` imports `PluginIntegrityVerifier` (zero hits outside the security package/tests/ADRs). Evidence grade: **A** (full-file reads, not grep inference; independently re-confirmed by two research roles tonight). Not selected as tonight's candidate (SCAN surface, lighter-weight; also correctly out of scope for an `intelligence` DEEP night) — but this is the single most actionable finding across all three of tonight's surfaces (every real external comparator — npm provenance, VS Code Marketplace, Chrome Web Store, even the bare MCP spec plus NSA/CISA guidance — has *some* enforced or independently-verifiable install-time control; Ruflo's is currently cosmetic). Strong, concretely-scoped (<300 lines: wire the existing tested class behind the existing dead `--verify` flag, warn-only default per ADR-145's own rollout plan) candidate for the next `capabilities` night.
